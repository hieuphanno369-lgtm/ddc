# DDC Control Tower — Core Map

Next.js 14 App Router app (Vietnamese ERP / project-progress dashboard). Root layout:
- `app/` = routes only, at repo root (NOT `src/app`). `app/[locale]/(app)/...` = authenticated shell pages (overview, projects, projects/[id], report, alerts, compliance, audit, admin, import, data-dictionary, data-schema, nhap-lieu). `app/[locale]/login` and `app/[locale]/not-found` sit outside the `(app)` group (no shell). `app/api/*` = route handlers.
- `src/lib/` = pure business logic (clock, evm, stages, daily-series, thresholds, format, password, rate-limit, uploads, activity, session).
- `src/server/` = data access + server actions (`queries.ts`, `project-queries.ts`, `actions.ts`, `authz.ts`, `validation.ts`, `report.ts`) plus `src/server/repo/` (repo abstraction).
- `src/components/` = UI grouped by domain (dashboard, admin, alerts, form, layout, project, ui).
- `prisma/` = `schema.prisma`, `migrations/`, `seed.ts`, `rls.sql` (RLS policy defined but not yet applied to the DB).

Invariants:
- Repo abstraction: import through `src/server/repo/index.ts`, never `prisma-repo.ts`/`mock-repo.ts` directly. `mock-repo.ts` (sync, in-memory) backs tests; `prisma-repo.ts` (async) backs the real DB — keep both in sync via `src/server/repo/types.ts` when the interface changes.
- Clock is virtualized: read "today" via `src/lib/clock.ts`, never `new Date()` in business logic. `DDC_FAKE_TODAY` override is guarded to non-production only.
- Fact/progress tables are append-only: rows carry `version`/`isLatest`, never UPDATE-in-place.
- Per-project read authz goes through `src/server/authz.ts` (`requireProjectRead()`) — Admin/BOD see all projects, Data-entry/Viewer only projects listed in `project_assignments`. This was retrofitted after most routes already existed — verify a given route actually calls it, don't assume.
- Manpower is stored PER SHIFT (`fact_daily_manpower.shiftCode` → `dim_shift`, open-ended code list, currently `morning`/`evening`); daily totals = sum of shifts (`src/lib/shifts.ts`, done in the repo layer). Never add fixed per-shift columns. Gotcha: since P2A code `afternoon` MEANS the EVENING shift (ca tối) — code kept, label changed; always render shift names from `dim_shift`, never hardcode "chiều"/"afternoon".
- Stages (value chain, P7-C2 merged 2026-09-28) are DATA in `dim_stage` (`side` left/right, `isActive`, names per locale), read via `repo.getStages()` and passed down to pure functions in `src/lib/stages.ts`; never reintroduce hardcoded stage lists. No delete, only deactivate (allowed only when no project has weight > 0% for it). Writes to stages or per-project weights run in a transaction holding `pg_advisory_xact_lock(hashtext('dim_stage'))`; server rejects a weight set that differs from the active stage set (`stages_changed`). Creating a project requires `stageWeights` (`weights_required`), written in the same transaction as the project.
- Equipment is entered PER DAY (no shift). Editing a past day (manpower/equipment) requires a reason (`reason_required`, min length in `src/server/actions-entry.ts`) that is stored in `audit_log.note`.
- Alert engine (T11): `src/lib/alert-rules.ts` = pure rules R1–R7; `src/server/alert-engine.ts` writes new alerts (dedup inside `repo.insertEngineAlerts`). Every save action calls `runAlertEngineSafe(projectId)` (never throws, must not break the save) — new write actions affecting progress/resources must call it too. Closing an alert requires an action note.
- Background jobs: `src/server/jobs.ts` `runJob()` always records a `job_run` row and never throws; triggered by external cron via `POST /api/cron/[job]` (only `alerts_daily` since P3E; it also prunes old auth rows) with `Authorization: Bearer $CRON_SECRET` (timing-safe compare). No in-process scheduler.
- FX rates: entered manually by admin only (Vietcombank auto-fetch removed in P3E, 2026-09-28).
- Notification secrets (webhook URL, SMTP password — P3B) must be encrypted with `src/lib/secret-box.ts` (AES-256-GCM, key env `NOTIFY_SECRET_KEY`) before storing in `notify_channel` (admin UI + sending since P3B).
- Project code (mã CT, `dim_project.currentAliasCode`) is unique case-insensitively (index `lower(...)` created in raw SQL, Prisma cannot express it - rerun `prisma migrate diff` after Prisma upgrades so it is not dropped). Pattern `M-\d+` is reserved for auto-generated `masterCode`: blocked on create and on code change (`isReservedProjectCode`). Writes take `pg_advisory_xact_lock(hashtext(lower(code)))` and re-check with `tx`.
- At most 1 PIC per project (partial unique index `project_assignments_one_pic_key`). Map Prisma P2002 via `isP2002On(e, targets)` (`prisma-repo-form.ts`), never blanket-catch P2002.
- Data-entry ALWAYS has finance visibility (T-1, permanent decision QĐ-10); `canViewFinance` per user applies to BOD/viewer.
- Finance visibility is fail-closed (`canViewFinance ?? false`); pages must self-check role, not rely on middleware alone.
- Auth (P3D-B, merged 2026-09-26): two independent layers. `middleware.ts` redirects to `/{locale}/login` when there is no session (or `token.invalid`); every `(app)` page AND the layout call `requireUser(locale, roles?)` (`src/lib/require-user.ts`) as the first await, because `redirect()` in the layout does not stop a page from streaming data. New pages must do the same (`app-pages-require-user.test.ts` fails otherwise); new `app/api/*` routes must be registered in `api-routes-guard.test.ts`. Path-param ids: validate `^[1-9]\d*$` before `Number()` (middleware matcher skips paths with a dot).
- Pass client components only the fields they render (mask money with `maskProjectSummaries` first, then narrow, e.g. `toTopPriorityItem` in `src/lib/top-priority.ts`); RSC props are visible in the payload.
- `src/lib/p3c-contract.ts` = temporary copies of 4 P3C data-contract types used by `EquipmentPlanGantt`/`ManpowerMonthChart`; account A deletes it when wiring those charts into the project detail page (P3C-A, ex Step 11 of P3C-B).
- 4 roles: Admin, BOD, Data-entry, Viewer. Auth = next-auth v4 credentials + Google OAuth (only emails already in the account list, `resolveAccess` fail-closed).
- Password security (P3E, 2026-09-28): all auth state goes through `AuthStore` (`src/server/auth-store.ts`, Prisma `prisma-repo-auth.ts` / memory `mock-repo-auth.ts`), not `repo`. Login rules in `src/server/login-guard.ts` (5 wrong = lock, admin unlocks; per-IP throttle; per-account guess slot `reserveAccountGuess`, kind `account_guess`, SHARED with change-password). Session JWT carries `pwdAt`; password change after that invalidates the session (checked every `ACCESS_RECHECK_INTERVAL_MS` = 5 min); `invalid` is sticky, never lowered back. The jwt `trigger === 'update'` branch may only tighten (public `POST /api/auth/session`). Self password change re-issues the cookie server-side (`reissueSessionCookie`), writes with compare-and-swap (`setPasswordIfHash`). Throttle rows use `pg_advisory_xact_lock` inside a transaction. Modals under a `.card`/`.side` with `backdrop-filter` must use `createPortal(document.body)`.

- Security headers + CSP report-only (P5-B, 2026-09-29): `middleware.ts` wraps the old auth logic in `route()`, then the outer `middleware` calls `applySecurityHeaders`/`withCspRequestHeaders` (`src/lib/security-headers.ts`) on EVERY branch (redirect, intl rewrite, 500, public) so all 6 headers + a fresh per-request nonce always land; the client's own `content-security-policy`/`content-security-policy-report-only`/`x-nonce` request headers are stripped first, never trusted. `app/[locale]/layout.tsx` reads the nonce via `headers()` for the inline theme-picker script — never cache that layout's render. New public POST endpoints follow `/api/csp-report`'s pattern (`app/api/csp-report/route.ts`, `src/lib/csp-report.ts`): check `rateLimit('<name>:global', ..., 60_000)` and return before computing the per-IP key (out of order = the per-IP `Map` grows unbounded, this was M1 in the security review), size cap read as a stream (never trust `Content-Length`), `stripControl` any string before logging (covers C0/C1/LS/PS/bidi override chars, not just `\n`). Must also stay registered in `api-routes-guard.test.ts`.
- Load test tooling (P5-B): `scripts/perf/load-test.ts` + `src/lib/load-test.ts` (stats in `src/lib/load-stats.ts`, percentile nearest-rank). Guarded to dev/loopback only (`assertPerfLocalBase`, `assertPerfDb` only `ddc_control_tower_b`, `assertOutsideRepo` for the accounts file) — do not relax these guards without also updating the guard tests. On the dev machine only ~30 virtual users meet the p95/p99 criteria (saturates at ~12-13 rps); 50/100 need re-measuring on the real P6 server, that is an infra result, not a code bug.
